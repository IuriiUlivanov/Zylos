# Требования к производительности Zylos

Нормы для v1: один город **Нови-Сад**, нативный Android + референс-веб, стек из [ARCHITECTURE.md](ARCHITECTURE.md).

Цифры — **обязательные SLO**, не пожелания. Фича не считается готовой, если она работает, но не укладывается в бюджет. Измерять на железе не слабее профилей ниже, не на машине разработчика в airplane mode.

---

## 1. Зачем отдельный файл

Карта 2ГИС ощущается быстрой: ввод буквы → подсказки, тап по дому → список организаций, маршрут за секунду. На одном городе это достижимо. Без порогов агент привезёт «правильный JSON за 4 секунды» и UI будет казаться сломанным.

---

## 2. Профили измерения

Считать нормой, не исключением.

### Клиент

| Профиль | Устройство | Сеть |
|---|---|---|
| **Web-mid** | 4 ядра, 8 GB RAM, Chrome последний, Full HD | 4G: 10 Мбит/с down, 5 Мбит/с up, RTT 50 мс |
| **Phone-mid** | Android 12, 4 GB RAM, MapLibre Native | та же 4G |
| **Slow** | Phone-mid | 3G: 2 Мбит/с, RTT 150 мс — только деградация, не основной SLO |

Сервер и клиент в одной локальной сети (dev) **не** являются профилем приёмки. Для приёмки API — либо RTT 20–50 мс до сервера, либо искусственный delay.

### Сервер v1

Один хост (или docker compose на одном ПК): **4 vCPU, 8 GB RAM, SSD**. На этом должны выполняться PostGIS + Meilisearch + Caddy/PMTiles + Valhalla + OTP + API одновременно. Если не влезает — резать OTP в отдельный профиль «transit cold start», не раздувать RAM в требованиях клиента.

Пиковая нагрузка v1: **50 одновременных сессий** карты, **10 запросов поиска/с**, **2 запроса маршрута/с**. Это не Google Maps; нормы ниже — про задержку, не про миллион RPS.

---

## 3. Как измерять

| Метрика | Инструмент |
|---|---|
| API latency | p50 / p95 / p99 за 5 минут, `Date` на ответе или OpenTelemetry |
| Поиск as-you-type | от `fetch` start до JSON, без отрисовки |
| Клик по зданию | от `touchend`/`click` до появления списка организаций в DOM |
| Кадр карты | Chrome Performance / `requestAnimationFrame`, не «на глаз плавно» |
| Тайлы | Network: время до первого видимого здания на z14 |
| Маршрут | от `POST /v1/route` до GeoJSON; отдельно время отрисовки линии |
| Бандл | `vite build` + размер gzip |

Повторяемость: **30 запросов** на сценарий после прогрева (первый запрос OTP/Valhalla может быть холодным — см. §6). В отчёт идут p95 по прогретым запросам **и** отдельно cold start.

Среда: extract Нови-Сада этапа 1 (~7 MB PBF, ~5 MB PMTiles), данные этапа 2 в PostGIS.

## 4. Карта (тайлы)

Файл `novi-sad.pmtiles` уже ~5 MB. Его не раздувать без нужды (maxzoom 14).

| ID | Требование | Порог | Профиль |
|---|---|---|---|
| T1 | Первая подложка после FCP: улицы видны | **≤ 1.5 с** | Web-mid / 4G |
| T2 | Здания видны на z14 в центре | **≤ 2.5 с** от открытия карты | Web-mid / 4G |
| T3 | HTTP Range к PMTiles | ответ **206**, TTFB **≤ 80 мс** localhost; **≤ 200 мс** p95 с RTT 50 мс | сервер тайлов |
| T4 | Пан/зум 14→16 | нет фризов **> 100 мс**; кадр карты **≥ 30 FPS** среднее за жест | Web-mid, Phone-mid |
| T5 | Размер архива PMTiles | **≤ 15 MB** для одного города v1 | артефакт |
| T6 | Параллельные range | не блокировать UI-поток; MapLibre worker | оба клиента |

На Slow (3G): T1 ≤ 4 с, T2 ≤ 6 с. Хуже — баг (слишком толстый стиль, нет overzoom, грузят весь PMTiles целиком вместо Range).

Запрещено: скачивать весь `.pmtiles` одним GET без Range; проксировать каждый тайл через Fastify.

## 5. Старт приложения

| ID | Требование | Порог |
|---|---|---|
| L1 | JS+CSS основного экрана (gzip) | **≤ 350 KB** без MapLibre; **≤ 900 KB** вместе с MapLibre |
| L2 | Time to interactive: карта + поле поиска | **≤ 3.5 с** Web-mid 4G, **≤ 5 с** Phone-mid 4G |
| L3 | Первый экран без аккаунта | 0 редиректов «подождите логин» |
| L4 | Шрифты карты | glyphs с своего origin или заранее известный CDN; не блокировать T2 на 10 с |

Capacitor: холодный старт WebView до интерактивной карты **≤ 6 с** Phone-mid (после установки, тайлы с сервера, не офлайн).

## 6. Поиск

Сценарий: пользователь вводит «futo» / «apoteka» / «булевар» с debounce **150 мс**.

| ID | Требование | Порог |
|---|---|---|
| S1 | `GET /v1/search` p95 | **≤ 120 мс** CPU сервера; **≤ 200 мс** end-to-end при RTT 50 мс |
| S2 | Выдача | первые **≤ 15** документов, не 500 |
| S3 | Отмена | устаревший ответ не перерисовывает список (ignore stale) |
| S4 | Пустой `q` или `q.length < 2` | **≤ 20 мс**, без удара в Meilisearch или с мгновенным empty |
| S5 | Индексация после editorial | документ находится по имени **≤ 5 с** после `PUT` |
| S6 | Память Meilisearch | индекс Нови-Сада **≤ 300 MB** RSS |

Fallback Photon: p95 **≤ 400 мс**. Если Photon медленнее — не блокировать Meilisearch: параллелить или только при 0 хитов.

## 7. Справочник и здания

| ID | Требование | Порог |
|---|---|---|
| B1 | `GET /v1/orgs/:id` p95 | **≤ 80 мс** сервер |
| B2 | `GET /v1/buildings/at` p95 | **≤ 100 мс** сервер (GIST, точка) |
| B3 | `GET /v1/buildings/:id` p95 | **≤ 150 мс** (контур + ≤ 100 организаций) |
| B4 | Клик по зданию до списка в UI p95 | **≤ 350 мс** Web-mid |
| B5 | Пины в bbox `GET /v1/orgs` | **≤ 200** объектов за запрос; p95 **≤ 150 мс** |
| B6 | GeoJSON контура здания | **≤ 50 KB**; упростить `ST_Simplify` для ответа, полный контур можно для hit-test |
| B7 | Здание без организаций | ответ всё равно **в бюджете B2/B3**, пустой массив, не 5 с |

Нарушение B2 обычно значит отсутствие GIST или запрос по всей таблице без `ST_DWithin`.

## 8. Маршруты

Прогретый граф (после `/status` healthy). Точки внутри `city_boundary`.

| ID | Режим | p95 API | p99 API | Timeout клиента |
|---|---|---|---|---|
| R1 | walk | **≤ 400 мс** | ≤ 800 мс | 3 с |
| R2 | bike | **≤ 400 мс** | ≤ 800 мс | 3 с |
| R3 | car | **≤ 500 мс** | ≤ 1 с | 3 с |
| R4 | transit (OTP) | **≤ 1.5 с** | ≤ 3 с | 8 с |

| ID | Требование | Порог |
|---|---|---|
| R5 | Холодный старт Valhalla после `compose up` | первая успешная прокладка **≤ 30 с**; дальше R1–R3 |
| R6 | Холодный старт OTP | **≤ 90 с** до healthy; не блокировать walk/car |
| R7 | Геометрия линии в ответе | **≤ 200 KB** GeoJSON; упрощать для UI |
| R8 | Вне города | **422 за ≤ 30 мс**, без вызова OTP «на Белград» |
| R9 | Отрисовка линии на карте | **≤ 100 мс** после JSON, 30 FPS во время addLayer |

Нет live пробок — не имитировать их задержкой.

## 12. Деградация (должно быть быстро даже в ошибке)

| Ситуация | Требование |
|---|---|
| Meilisearch down | `GET /search` **≤ 150 мс** с 503 и телом ошибки, не 30 с hang |
| Valhalla down | `POST /route` mode=car **≤ timeout 3 с**, код 504 |
| OTP down | car/walk живы в своих бюджетах |
| Точка в Футоге vs центр | тот же бюджет B2 (не «на окраине медленнее в 20 раз») |

---

## 13. Что не нормируем в v1

- Миллионы пользователей, мультирегион, CDN по миру.
- Indoor ТЦ, 3D, пробки.
- Офлайн-роутинг на телефоне (офлайн PMTiles — отдельный этап, тогда T1/T2 с диска **≤ 800 мс**).
- Идеальный 60 FPS на low-end 2 GB Android.
- Сравнение «как облачный Google» по глобальному geocoder latency.

---

## 14. Приёмка фичи

В PR / отчёте агента для экрана или эндпоинта:

1. ID порога из этого файла (например B4, S1, R3).
2. Профиль (Web-mid / Phone-mid).
3. p50 и p95, n ≥ 30, прогрев да/нет.
4. Если порог не взят — фича **не** done.

Не заменять замер скриншотом карты.
